Vision merging

Merging 8 tasks into 1 model cost ~24 points

Average accuracy, % — 8 CLIP ViT-B/32 specialists vs. the merged model

Backbone: CLIP ViT-B/32 (OpenAI-pretrained), fine-tuned separately into 8 task specialists — Cars, DTD, EuroSAT, GTSRB, MNIST, RESISC45, SUN397, SVHN — then combined into one shared model via task_arithmetic (α = 0.3). Toolkit: merge-and-rebase.

task_arithmetic — compute each task's vector (tuned weights − base weights), scale every one by α, sum all 8, add to base (Editing Models with Task Arithmetic, ICLR 2023).

76.5% of specialist accuracy survives the merge, on average — the rest is interference between the 8 tasks fighting over the same shared weights.

LLM merging — method 1 of 4

Linear

Plain weighted average of the raw checkpoint weights — no task-vector math at all (Model Soups, ICML 2022).

Recipe: Base (weight 0.34) + Qwen-Instruct (0.33) + Dolphin (0.33) — all three, roughly equally.

The simplest of the four, and no bugs encountered building it. Neither benchmark shows a statistically significant difference from Base — if anything it edges slightly above Base on both, but well within noise. A safe, unremarkable default.

LLM merging — method 2 of 4

TIES

Trims each task vector to its largest changes, resolves sign disagreements between models by majority vote, merges only the survivors (TIES-Merging, NeurIPS 2023).

Recipe: base_model = Base; sources = Qwen-Instruct (weight 0.5) and Dolphin (weight 0.5) — both equally.

ARC-Easy (acc_norm, %)
PIQA (acc_norm, %)
TIES vs. Base — McNemar's exact test
Taskp-valueVerdict
ARC-Easy0.041significant, uncorrected only

ARC-Easy shows a marginal result vs. Base (p=0.041) — the weakest signal that still clears the standard 0.05 threshold, and it does not survive a Bonferroni correction across the 8 tests run overall (see the pooled slide). Treat it as suggestive, not proven. PIQA is a near-exact coin flip vs. Base (p=1.000).

LLM merging — method 3 of 4

DARE-TIES

Same sign-consensus step as TIES, but keeps parameters via random pruning instead of magnitude, then rescales the survivors (Language Models are Super Mario, 2023).

Recipe: identical structure to TIES — Base as base_model; Qwen-Instruct + Dolphin as equal-weighted sources.

ARC-Easy (acc_norm, %)
PIQA (acc_norm, %)
DARE-TIES vs. Base — McNemar's exact test
Taskp-valueVerdict
ARC-Easy4.1 × 10⁻¹⁶significant, survives correction
PIQA0.015significant, uncorrected only

The one method with a real story. Running it in float16 silently corrupted the model's embedding weights with NaNs — no error from the tool, only caught by scanning the output weights directly (see “bugs found”). Even after fixing that (switching to bfloat16), it's the clear worst performer: the ARC-Easy gap vs. Base is overwhelming (p=4.1×10⁻¹⁶, survives any correction), and it's the only method whose PIQA gap is even nominally significant (p=0.015), though that one doesn't survive correction. Qualitatively it also produced the most broken output of the four — a repeated “!!!!” loop on one prompt, a wrong arithmetic answer on another.

LLM merging — method 4 of 4

Arcee Fusion

Scores every parameter by (size of change × how much it shifts the output distribution), fuses only what clears a dynamic per-tensor threshold. Strictly pairwise, so combining 3 models needed a two-stage cascade — fusing Qwen-Instruct into Base, then Dolphin into that result (Arcee AI release blog — no paper).

Recipe: two-stage — stage 1 fuses Qwen-Instruct into Base; stage 2 fuses Dolphin into that result. Touches Base, then Instruct, then Dolphin, sequentially.

LLM merging — statistical test

Pooling "unmerged" vs. "merged" — is that valid?

A naive way to ask this — average the 3 unmerged models' items against the 4 merged models' items and run a proportions test — would be wrong: it treats 16,632 (item × model) rows as independent, when the same 2,376 or 1,838 items repeat across all 7 models. The correct tool is GEE (Generalized Estimating Equations) with a binomial family, clustering by item — this gives valid standard errors despite that repetition, so pooling is statistically appropriate once done this way.

GEE, clustered by item — pooled odds ratio (merged vs. unmerged), all 16,632 / 12,866 (item × model) observations
ComparisonTaskOdds ratiop-valueVerdict
All 4 merges vs. 3 unmergedARC-Easy0.8836.7 × 10⁻¹⁵significant — merged worse
All 4 merges vs. 3 unmergedPIQA0.9890.435not significant
Excl. DARE-TIES (3 merges) vs. 3 unmergedARC-Easy0.9510.0011significant, much smaller
Excl. DARE-TIES (3 merges) vs. 3 unmergedPIQA1.0160.255not significant

So: yes, pooled comparison is valid here, and it does show a real effect on ARC-Easy — merged models are collectively worse than unmerged ones (OR 0.88, p≈10⁻¹⁵). But most of that comes from DARE-TIES: drop it, and the effect shrinks by more than half (OR 0.95) while staying significant (p=0.0011) — so even the three "good" methods carry a small, real, detectable cost on ARC-Easy when pooled for extra power, on top of DARE-TIES's much larger one. On PIQA, pooling changes nothing: no significant effect either with or without DARE-TIES. The per-method table above is still the more informative view for deciding what to do about any specific method — this pooled result answers a different, narrower question: "does merging in general cost something on average," and the answer is a qualified yes on ARC-Easy, no on PIQA.

All three patterns are real: merging can rescue an answer only one source knew (Jupiter), invent a wrong answer neither source gave (−40°C), or lose an answer every relevant source had (96) — the outcome depends on the specific fact and method, not a fixed rule.

Takeaways

Three findings that held in both experiments

A

Merging always costs something

True in vision (90.4% → 69.7%) and language models (the best unmerged model beat every merge on ARC-Easy).

B

Gentler methods lose less

Selective approaches (TIES, Arcee Fusion, even plain linear averaging) consistently beat aggressive ones (raw task arithmetic, DARE's random pruning).

C

The damage isn't even

Narrow, simple capabilities survive merging almost intact; broad, entangled ones take the real hit.

Fixed

Stale checkpoint filenames in 2 shipped configs — patched both.

Fixed

Dead debug config pointed at a file that doesn't exist — repointed it.

Recommendations

What I'd suggest next

01

Consult with the stakeholders — align on priorities and a real target use case before committing further effort.

02

Focus on LLM merging before multimodality — the language-model results are the flatter, safer surface to iterate on next; vision merging's larger, uneven damage can wait.

03

Redirect effort toward MergeKit and stronger models — the small proxy models have done their job; point the same method comparison at something we'd actually deploy, e.g. Gemma.

04

Consider the OLMo family — Ai2's newly released OLMo 3 (fully open weights and training data) is a strong next candidate.

05

Keep experimenting and expand eval coverage — 2 benchmarks was enough to find a signal, not enough to fully trust it.

06

Report the bugs found — the merge-and-rebase config issues and MergeKit's silent NaN corruption should go back to their maintainers.
